# 프로젝트 공유 리액션 설계

## 1. 배경

현재 `# 업무-프로젝트`와 `# 사이드-프로젝트`에는 `reactionSets`에서 가져온
임의의 이모지와 숫자가 표시된다. 이 값은 콘텐츠나 방문자 행동과 연결되지
않으며, 클릭하거나 저장할 수 없는 장식이다.

이 장식을 실제 공유 리액션으로 교체한다. 방문자는 로그인 화면 없이
프로젝트에 반응할 수 있고, 같은 프로젝트를 보는 다른 방문자도 저장된
숫자를 확인한다. 리액션 데이터는 GitHub Pages 배포와 분리해 사이트를
다시 빌드하거나 배포해도 유지한다.

## 2. 목표와 제외 범위

### 목표

- `# 업무-프로젝트`와 `# 사이드-프로젝트`의 각 프로젝트에
  `👍`, `🔥`, `🎉`, `👏` 리액션을 제공한다.
- 데스크톱에서는 프로젝트 메시지에 호버하거나 키보드 포커스가 들어올 때
  액션 바를 표시한다.
- 모바일에서는 프로젝트 메시지를 탭해 액션 바를 열고, 바깥을 탭해 닫는다.
- 방문자는 로그인하지 않고 반응한다.
- 한 방문자는 한 프로젝트의 각 이모지를 한 번씩 선택할 수 있다. 서로 다른
  이모지는 동시에 선택할 수 있다.
- 선택한 이모지를 다시 누르면 반응을 취소한다.
- 클릭한 화면은 즉시 갱신하고, 다른 방문자는 새로고침하거나 다시 방문할
  때 최신 숫자를 받는다.
- 같은 프로젝트의 한국어와 영어 페이지는 하나의 리액션 데이터를 공유한다.
- 리액션 숫자는 사이트 배포와 무관하게 영구 보존한다.

### 제외 범위

- `# 경력`, `# 기술`, `# 학력-자격` 채널의 리액션
- 검색 가능한 전체 이모지 선택기나 사용자 정의 이모지
- GitHub 또는 다른 계정을 이용한 방문자 로그인
- 기기 간 방문자 식별 동기화
- 이미 페이지를 열어 둔 다른 방문자에게 보내는 실시간 푸시
- Pages CMS에서 리액션 숫자를 직접 편집하는 기능
- 관리자 통계·삭제·차단 화면
- 로그인 없는 환경에서 불가능한 완전한 봇·조작 방지

## 3. 사용자 경험

### 데스크톱과 키보드

프로젝트 메시지 오른쪽 위에 액션 바를 배치한다. 포인터가 해당 메시지에
올라간 동안만 네 개의 이모지 버튼을 표시한다. 키보드 사용자는 메시지나
버튼에 포커스가 들어오면 같은 액션 바를 볼 수 있으며 `Escape`로 닫을 수
있다.

이미 1개 이상의 반응이 있는 이모지는 메시지 아래에 `👍 3` 형태의 카운트
칩으로 계속 표시한다. 카운트 칩도 버튼이며, 누르면 해당 방문자의 반응을
추가하거나 취소한다. 방문자가 선택한 칩과 액션 버튼은 선택 색상을 사용한다.

### 모바일

호버가 없는 포인터 환경에서는 프로젝트 메시지를 한 번 탭해 해당 메시지에
포커스를 주고 액션 바를 표시한다. 다른 곳을 탭하거나 `Escape`를 누르면
닫는다. 프로젝트 링크, 기존 태그, 배지, 리액션 버튼을 직접 탭한 경우에는
메시지 포커스 토글이 그 동작을 가로채지 않는다.

### 표시 규칙

- 초기 실제 데이터는 모든 프로젝트에서 0부터 시작한다.
- 현재 하드코딩된 임의 숫자는 마이그레이션하지 않고 삭제한다.
- 숫자가 0인 이모지는 카운트 칩으로 표시하지 않는다.
- 액션 바에는 항상 고정된 네 이모지를 모두 표시한다.
- 태그와 사이드 프로젝트 배지는 현재 모습과 의미를 유지한다.
- JavaScript가 없거나 리액션 API가 준비되지 않은 동안에는 동작하지 않는
  버튼이나 가짜 숫자를 표시하지 않는다.

## 4. 시스템 구조

```text
GitHub Pages의 Astro 포트폴리오
        │
        │ HTTPS JSON API
        ▼
Cloudflare Worker 리액션 API
        │
        │ D1 바인딩
        ▼
Cloudflare D1 영구 데이터베이스
```

Astro 사이트는 프로젝트 마크업, 호버·탭 인터랙션, 낙관적 UI 갱신과
현재 리액션 대상 목록을 담은 `/reaction-targets.json` 정적 매니페스트를
담당한다. Cloudflare Worker는 공개 브라우저와 데이터베이스 사이의 유일한
쓰기 경계로서 요청 검증, 대상 매니페스트 확인, 익명 방문자 토큰, 요청
제한, CORS, D1 접근을 담당한다. D1은 사이트 저장소 및 GitHub Pages 배포
이력과 독립적으로 리액션을 저장한다.

Worker와 D1 코드는 같은 저장소의 `services/reactions/` 아래에 둔다.
프런트엔드는 공개 API 주소만 사용하며 D1 자격 증명이나 Worker 비밀값을
포함하지 않는다. API 주소는 `PUBLIC_REACTIONS_API_URL` 빌드 변수로
주입한다.

## 5. 프로젝트 식별

프로젝트 표시 이름이나 번역문은 수정될 수 있으므로 리액션 키로 사용하지
않는다. Astro 콘텐츠 엔트리의 파일 ID를 정규화해 안정적인
`targetId`를 만든다.

```text
src/content/projects/samsung-agenthub.ko.yaml
src/content/projects/samsung-agenthub.en.yaml
→ work:samsung-agenthub

src/content/sideProjects/booster.ko.yaml
src/content/sideProjects/booster.en.yaml
→ side:booster
```

정규화 함수는 업무 프로젝트에 `work:`, 사이드 프로젝트에 `side:`
접두사를 붙이고 `.ko` 또는 `.en` 언어 접미사와 파일 확장자를 제거한다.
이 때문에 한국어와 영어 엔트리가 같은 키를 사용하면서 두 프로젝트
컬렉션의 이름 충돌은 피한다.

Pages CMS는 컬렉션 파일 이름 바꾸기를 허용하지 않으므로 본문, 제목,
정렬 순서, 태그, 배지를 수정해도 `targetId`는 유지된다. 프로젝트를
삭제하면 기존 D1 행은 자동 삭제하지 않지만, 사이트에서 더 이상 해당 ID를
요청하지 않으므로 노출되지 않는다. 같은 파일 ID로 프로젝트를 다시 만들면
기존 리액션과 다시 연결된다.

Astro 빌드는 페이지가 실제로 `# 업무-프로젝트`와
`# 사이드-프로젝트`에 렌더링하는 엔트리에서만 언어 중복을 제거한
`targetId` 목록을 `/reaction-targets.json`에 생성한다. 이 배포된
매니페스트가 유효한 프로젝트의 권위 있는 목록이다. Worker는 HTTPS로
매니페스트를 가져와 성공한 목록을 최대 5분간 캐시하고, bootstrap과 쓰기
모두에서 목록에 없는 ID를 거부한다. 유효한 캐시가 없는 상태에서
매니페스트 조회도 실패하면 안전하게 요청을 거부한다. 프로젝트 삭제 후
최대 캐시 시간까지는 기존 ID가 허용될 수 있지만 그 이후에는 쓰기가
중단된다.

```json
{
  "version": 1,
  "targets": ["side:booster", "work:samsung-agenthub"]
}
```

매니페스트는 중복 없는 오름차순 배열로 생성하고 Worker의
`REACTION_TARGET_MANIFEST_URL` 공개 환경 변수로 위치를 설정한다.

## 6. 데이터 모델

D1에는 집계 숫자를 별도로 저장하지 않고 방문자별 선택 행을 저장한다.

```sql
CREATE TABLE reactions (
  target_id TEXT NOT NULL,
  emoji TEXT NOT NULL,
  visitor_hash TEXT NOT NULL,
  created_at TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP,
  PRIMARY KEY (target_id, emoji, visitor_hash)
);

CREATE INDEX reactions_target_emoji
  ON reactions (target_id, emoji);
```

복합 기본 키가 한 방문자의 같은 프로젝트·이모지 중복을 데이터베이스
수준에서 방지한다. 카운트는 `target_id`와 `emoji`로 그룹화해 계산한다.
현재 데이터 규모에서는 별도 집계 테이블이나 캐시를 두지 않는다.

`emoji`는 Worker에서 네 개의 허용값으로 검증한다. `target_id`는
`^(work|side):[a-z0-9]+(?:-[a-z0-9]+)*$` 형식과 최대 96자만 허용한다.
Bootstrap 요청은 중복을 제거한 프로젝트 100개와 16KiB JSON 본문까지만
받는다.

## 7. 익명 방문자 식별과 보호

첫 bootstrap 요청에 유효한 토큰이 없으면 Worker가 암호학적으로 임의인
방문자 ID를 만들고 Worker 비밀값으로 HMAC 서명한 불투명 토큰을 돌려준다.
브라우저는 이 토큰을 전용 `localStorage` 키에 저장한다. 이후 요청은
`Authorization: Bearer <token>` 헤더로 토큰을 보낸다.

Worker는 서명을 검증한 뒤 방문자 ID의 해시만 D1의 `visitor_hash`로
사용한다. 원본 IP, User-Agent, 이메일과 같은 개인 식별 정보는 D1에
저장하지 않는다.

이 방식의 경계는 다음과 같다.

- 같은 브라우저 저장소에서는 새로고침과 사이트 재배포 후에도 방문자 선택을
  복원한다.
- 브라우저 저장소를 지우거나 다른 브라우저·기기를 사용하면 새 방문자로
  인식한다.
- 서명 없는 임의 방문자 ID는 쓸 수 없지만, 사용자가 저장소를 반복해서
  지워 새 토큰을 받는 행위를 완전히 막지는 않는다.

Worker는 Cloudflare Workers Rate Limiting 바인딩으로
`write:<visitorHash>` 키별 60초당 30회의 쓰기 요청 제한을 적용한다.
새 토큰 발급은 `issue:<HMAC(requestIp)>` 임시 키별 60초당 20회까지
허용하되 그 키나 IP를 D1에 저장하지 않는다. 이 제한은 정상 방문자를
막지 않으면서 자동화된 대량 생성을 완화하기 위한 것이며 완전한 사용자
신원 증명은 아니다.

CORS 허용 목록은 운영 사이트 `https://kybee.github.io`와
`http://localhost:4321`, `http://127.0.0.1:4321` 로컬 개발 Origin으로
제한하고, 그 외 Origin에는 CORS 응답 권한을 주지 않는다. CORS는 브라우저
호출 범위를 제한할 뿐 API 인증을 대신하지 않으므로 모든 쓰기는 별도로
서명 토큰과 요청 제한을 검증한다.

## 8. API 계약

일반 API 응답은 JSON이며 `Cache-Control: no-store`를 사용한다. 교차
Origin 사전 요청인 `OPTIONS`는 본문 없는 `204`로 응답한다. 허용 Origin을
정확히 반영하고 `Vary: Origin`,
`Access-Control-Allow-Methods: POST, PUT, OPTIONS`,
`Access-Control-Allow-Headers: Authorization, Content-Type`를 보낸다.
사전 요청은 JSON 본문과 방문자 토큰 검증 대상이 아니지만 Origin과 요청
메서드·헤더는 검증한다. 실제 API 요청은 허용된 Origin, `Content-Type`,
본문 크기, 필드 타입을 먼저 검증한다.

### `POST /v1/reactions/bootstrap`

페이지에 있는 모든 업무·사이드 프로젝트의 현재 상태를 한 번에 조회한다.
유효한 방문자 토큰은 선택 사항이며, 없거나 손상된 경우 새 토큰을 발급한다.

```json
{
  "targets": [
    "work:samsung-agenthub",
    "side:booster"
  ]
}
```

```json
{
  "visitorToken": "v1.<opaque-payload>.<signature>",
  "reactions": {
    "work:samsung-agenthub": {
      "counts": {
        "👍": 3,
        "🔥": 1,
        "🎉": 0,
        "👏": 0
      },
      "selected": ["👍"]
    }
  }
}
```

### `PUT /v1/reactions`

UI는 토글처럼 보이지만 API에는 원하는 최종 상태를 명시한다. 이 계약은
요청이나 응답이 유실되어 같은 요청을 재시도해도 상태가 두 번 뒤집히지
않게 한다.

```json
{
  "targetId": "work:samsung-agenthub",
  "emoji": "🔥",
  "active": true
}
```

```json
{
  "targetId": "work:samsung-agenthub",
  "emoji": "🔥",
  "active": true,
  "count": 2
}
```

`active: true`는 `INSERT OR IGNORE`, `active: false`는 조건부 `DELETE`로
처리한다. 상태 변경문과 바로 뒤의 카운트 `SELECT`는 하나의 D1
`batch()` 트랜잭션으로 실행해 함께 성공하거나 함께 롤백한다. D1이 배치를
순서대로 실행하므로 응답 카운트는 해당 요청의 쓰기가 반영된 값이다.
그 뒤 도착한 다른 방문자의 동시 요청으로 숫자가 다시 달라질 수 있으며,
다음 bootstrap은 그 최신값을 반환한다. 쓰기에는 유효한 방문자 토큰이
필수다.

오류 상태는 다음 의미를 갖는다.

- `400`: 허용되지 않은 ID, 이모지, 타입 또는 요청 크기
- `401`: 쓰기에 필요한 방문자 토큰이 없거나 유효하지 않음
- `403`: 허용되지 않은 Origin
- `404`: 배포된 대상 매니페스트에 없는 프로젝트 ID
- `429`: 요청 제한 초과
- `503`: 유효한 대상 매니페스트를 가져오거나 캐시할 수 없음
- `500`: 예상하지 못한 Worker 또는 D1 오류

## 9. 프런트엔드 구성과 데이터 흐름

`Workspace.astro`는 콘텐츠 엔트리 자체를 유지해 파일 ID를 사용할 수 있도록
정렬된 프로젝트 뷰 모델을 만든다. 각 대상 메시지에는 정규화된
`data-reaction-target`을 렌더링한다. 현재의 전역 `reactionSets`와 임의
숫자 렌더링은 제거한다.

리액션 마크업은 재사용 가능한 작은 컴포넌트로 분리한다. 각 메시지에는
항상 키보드로 접근 가능한 `리액션 열기` 버튼을 두고 프로젝트 이름이
포함된 `aria-label`, `aria-expanded`, 액션 패널을 가리키는
`aria-controls`를 설정한다. 버튼은 메시지가 기본 상태일 때 시각적으로
절제하되 `Tab` 포커스를 받으면 즉시 보이게 한다.

클라이언트 컨트롤러는 동시에 하나의 액션 패널만 명시적인 열린 상태로
관리한다. 포인터 진입, 열기 버튼의 `Enter`·`Space`, 호버 없는 환경의
메시지 탭은 해당 패널을 연다. 다른 메시지를 열면 이전 패널을 닫는다.
포인터가 메시지를 벗어나고 내부 포커스도 없으면 닫으며, 바깥 탭은 모바일
패널을 닫는다. `Escape`는 패널을 닫고 `aria-expanded`를 `false`로 바꾼
뒤 열기 버튼으로 포커스를 돌린다. 닫힌 패널의 이모지 버튼은 탭 순서에
들어가지 않는다.

데이터 컨트롤러는 다음 한 가지 공개 계약만 사용한다.

1. 페이지의 모든 `[data-reaction-target]`을 수집한다.
2. bootstrap을 한 번 호출해 카운트와 방문자 선택을 받는다.
3. 1개 이상인 카운트 칩을 렌더링하고 액션 버튼을 활성화한다.
4. 클릭하면 해당 이모지의 원하는 `active` 상태를 계산한다.
5. UI를 즉시 낙관적으로 갱신하고 같은 버튼의 중복 요청을 잠근다.
6. Worker 응답의 최종 카운트와 상태로 맞춘다.
7. 실패하면 이전 상태로 되돌리고 접근 가능한 짧은 오류 상태를 알린다.

다른 방문자의 변경을 자동 폴링하거나 구독하지 않는다. 각 페이지 로드의
bootstrap과 현재 방문자의 쓰기 응답만 최신 상태를 가져온다.

## 10. 오류 처리와 접근성

Bootstrap을 기다리는 동안 리액션 컨트롤은 숨긴다. 실패하면 프로젝트
본문, 링크, 태그, 배지는 정상적으로 유지하고 리액션 숫자를 0으로
가장하지 않는다. 대신 해당 채널 끝에 작은 `리액션 다시 시도` 버튼과
`aria-live` 상태를 한 번 표시한다. 재시도 성공 시 버튼을 제거하고 정상
컨트롤을 활성화한다. 이 오류를 전체 페이지 오류로 승격하지 않는다.

쓰기 실패 시 낙관적 변경을 되돌리고 해당 메시지 가까이에 짧은 상태
메시지를 표시한다. 네트워크 오류나 `429`에 대해 자동으로 상태 변경
요청을 반복하지 않는다. 사용자가 다시 누르면 새 요청을 보낼 수 있다.

모든 이모지 액션은 실제 `button`을 사용하고 `aria-label`, 선택 상태,
키보드 `Enter`와 `Space`, 보이는 포커스 스타일을 제공한다. 상태 알림은
`aria-live="polite"`를 사용한다. CSS 호버만으로 기능을 잠그지 않고
명시적인 열린 상태와 포커스 이동 규칙을 사용한다.

## 11. 배포와 데이터 수명

Worker 배포와 D1 마이그레이션은 GitHub Pages 배포와 별도 단계다. 최초
구성에는 사용자의 Cloudflare 로그인 또는 승인이 필요하다. 그 승인 뒤
D1 생성, 원격 마이그레이션 적용, Worker HMAC 비밀값 등록, Worker 배포,
운영 API 확인 순으로 한 번 설정한다.

저장소에는 `services/reactions/**` 변경 시 Worker 테스트와 원격 D1
마이그레이션을 거쳐 배포하는 별도 GitHub Actions 워크플로를 둔다. 이
워크플로는 `CLOUDFLARE_API_TOKEN`과 `CLOUDFLARE_ACCOUNT_ID` GitHub
Secrets를 사용한다. 운영 Worker URL은 공개 저장소 변수
`PUBLIC_REACTIONS_API_URL`로 기존 GitHub Pages 빌드에 전달한다. Worker
HMAC 비밀값은 Cloudflare Secret에만 저장하고 대상 매니페스트 URL은
Worker의 공개 환경 변수로 둔다. 기존 필수 `verify` 검사에는 Worker 단위
검사와 로컬 D1 통합 검사를 포함해 프런트엔드와 API가 같은 PR에서 함께
검증되게 한다.

초기 배포 순서는 Worker와 D1을 먼저 준비하고, 운영 API가 응답하는 것을
확인한 다음 저장소 변수와 프런트엔드를 배포하는 방식으로 고정한다.

D1 마이그레이션은 추가형으로 관리하며 사이트 재배포나 Worker 코드
롤백에서 테이블을 초기화하지 않는다. 따라서 콘텐츠 본문 수정, GitHub Pages
재배포, Worker 재배포 후에도 기존 리액션 행과 카운트가 유지된다.

처음 운영 배포할 때 현재 임의 숫자를 가져오지 않고 빈 D1 테이블에서
시작한다.

## 12. 검증

### 자동 검증

- 프로젝트 파일 ID에서 언어 접미사를 제거하고 컬렉션 접두사를 붙이는
  정규화 함수
- 한국어와 영어 엔트리가 같은 `targetId`를 생성하는 계약
- 업무 프로젝트와 사이드 프로젝트의 같은 파일명이 충돌하지 않는 계약
- 허용 이모지·ID·Origin·본문 크기 검증
- 정적 대상 매니페스트의 한·영 중복 제거와 알 수 없는 ID 거부
- `OPTIONS` 사전 요청의 허용 메서드·헤더·Origin과 `Vary: Origin`
- 익명 토큰 발급, 서명 검증, 손상된 토큰 거부
- Bootstrap의 카운트와 방문자 선택 복원
- 반응 추가, 같은 상태 재요청, 취소, 서로 다른 이모지 동시 선택
- 복합 키를 통한 중복 방지와 D1 배치의 쓰기·카운트 원자성
- API 실패 시 낙관적 프런트엔드 상태 롤백
- `# 업무-프로젝트`와 `# 사이드-프로젝트`에만 리액션 대상이 렌더링됨
- 기존 하드코딩 `reactionSets`와 임의 숫자가 빌드 결과에서 제거됨
- 열기 버튼의 이름·확장 상태, 한 번에 하나의 패널, Escape 포커스 복귀
- 기존 `npm run verify`와 Worker 로컬 D1 테스트

### 브라우저 검증

- 데스크톱에서 호버된 메시지에만 액션 바가 나타남
- 키보드 포커스에서도 같은 액션 바를 사용할 수 있음
- 모바일에서 메시지 탭으로 열리고 바깥 탭으로 닫힘
- 프로젝트 링크와 기존 태그·배지 동작이 가로채지지 않음
- 클릭과 취소가 즉시 보이고 새로고침 후 같은 상태가 복원됨
- 한국어에서 누른 반응이 영어 페이지에서도 같은 카운트로 보임
- API 중단 시 포트폴리오 콘텐츠는 계속 읽을 수 있음
- 사이트와 Worker를 다시 배포한 뒤에도 기존 D1 카운트가 유지됨

## 13. 완료 조건

- 두 프로젝트 채널의 하드코딩 리액션이 실제 공유 리액션으로 교체된다.
- 네 가지 고정 이모지가 합의한 웹 호버·모바일 탭 방식으로 동작한다.
- 익명 방문자는 이모지별로 한 번 추가하고 다시 눌러 취소할 수 있다.
- 한국어와 영어 페이지가 같은 프로젝트 카운트를 공유한다.
- 숫자는 0부터 시작하며 GitHub Pages 및 Worker 재배포 후에도 유지된다.
- 오류가 포트폴리오 본문 사용을 막지 않고 가짜 숫자를 만들지 않는다.
- 프런트엔드, Worker, D1 관련 자동 검사와 전체 사이트 검증이 통과한다.
